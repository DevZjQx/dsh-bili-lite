# 计划：抽帧 v3 —— 章节取帧 / 有效像素口径 / 格间分隔

**状态**：M1 / M2 已落地（2026-11-02，随 0.2.x 提交；`bun run check` 通过，真机 shots 回归待跑）；
M3 待实施（按 §4 修订后的选点策略）。目标批次 0.3.0
**关系**：只改 `bili-agent` 的 `shots`（`ops.ts`）、CLI 排版（`commands.ts`）、`bili-tools` 的 `bili_shots`
参数 / schema / render（`feature.ts`），以及 M3 所需的最小测试接线（`test/`、`package.json`、`tsconfig.json`）；
文档（README / `docs/features` / 本计划）与随仓库提交的 `dist` 同步；不碰 pulse / settings / 额度账本 / 写操作。
与「抽帧 v2」（指定时刻 / 区间去重 / 局部裁切）是增量关系，不改已有参数语义。
**目标**：把有限的格子放在画面真的变过的地方，并把「格子里到底能读到什么」写进返回值 ——
减少「拿一帧当账本」的事实错误，而不是追求更便宜的图。
**不在本计划内**：压缩域取帧（I 帧 + 运动向量）、16 FPS 密抽、模型侧 token 压缩、换视觉模型、
整条视频的自动切点扫描、帧落盘做跨进程长期缓存、下载整段视频。

**本稿修订（相对初稿）**：

- 把「画面高」和 `cellHeight` 分开记：`cellHeight = 画面 + 格号条`，初稿把 478 当成了返回值里的格子高。
- M1 的有效像素固定用「画面高」算，并按 `sheetWidth` / `sheetHeight` 现算、`scale ≤ 1`；523×293 是画面区，不是格子总高。
- M1 与 M2 的整图尺寸公式统一：M2 加 2px 后 `sheetWidth = cols × (cellWidth + 2)`、`sheetHeight = rows × (cellHeight + 2)`。
- M2 明确 `SHEET_MAX_WIDTH` 是软预算：3×3 加缝后 2562，超出 2px/格；token 估算按实际长边。
- M1 / M2 同批落地：`SHOTS_CACHE_VERSION` 7 → 8，旧 v7 缓存直接失效；回填只作为同版本缺字段的防御。
- M1 的 crop 口径：输出尺寸与裁切区域原生像素分开报，不把放大后的输出当「裁切后的尺寸」。
- M3 选点改为章节内 60% / 85% 帧优先，起点只作补充；超容量先保首尾；章节序号 C1..Cn 烧进格号条。
- M3 补 `chapters` 的数据契约（返回值 / 进度 / schema / render）、CLI 与工具参数面、失败不写缓存、确定性选点算法和测试前置。
- 验收条件按现状改写：无 ffmpeg / 整条取帧失败 / 播放直链 412 不会「退化成少画面」，只有章节接口失败和部分帧失败能退化。

## 1. 口径（本文所有数字的来源）

### 1.1 3×3 / 1080p / 有字体时（M1 口径；M2 加缝后的数字见 1.2）

`ops.ts:1167-1199`，`SHEET_MAX_WIDTH = 2560`：

| 量 | 值 | 怎么来的 |
|---|---|---|
| 画面 | 852×478 | `evenFloor(min(1920, floor(2560/3)))`，16:9 |
| 格号条 | 62px | `labelMetrics(852)`：字号 36，height = 56 + 2×3 |
| **cellHeight** | **540** | 画面 478 + 格号条 62 —— **不是 478** |
| 整图（M1，未加缝） | 2556×1620 | `852×3` × `540×3` |
| 缩到长边 1568 后画面 | 523×293 | `1568/2556 = 0.613`，852×478 同比例缩 |
| 缩到长边 1568 后格子总高（含格号条） | 523×331 | 540×0.613，含格号条 |
| 9 张独立 720p（1280×720） | ≈10.8k token | 28px patch：46×26 ×9，**估算** |
| 整图不缩 | ≈5.3k token | 92×58，同上 |
| 整图缩到长边 1568 | ≈2.0k token | 56×36，同上 |

M2 加缝后整图不缩约 5.4k token（92×59），缩到 1568 仍约 2.0k；差异不影响量级。

没有字体 / `drawtext` 时 `labels=false`，格号条不存在：`cellHeight = 478`，M1 整图 2556×1434（M2 加缝后 2562×1440），返回值也会是 852×478。
初稿说的「一格 852×478」只在这个条件下成立；有字体时实际返回值是 **852×540**，其中 62px 是格号条。

### 1.2 M2 加 2px 后（承接 1.1 的 1080p / 有字体）

每格右/下补 2px，tile 变成 `854×542`：

| 量 | 值 | 说明 |
|---|---|---|
| 画面 | 852×478 | 不变 |
| tile | 854×542 | 画面 + 2px 缝 |
| 整图 | 2562×1626 | `854×3` × `542×3` |
| 缩到长边 1568 后画面 | 521×293 | 1568/2562 = 0.612 |
| 缩到长边 1568 后 tile（含缝 / 格号条） | 523×332 | 542×0.612 |

实测（合成 testsrc2，1080p）：2562×1626 → 缩到 1568 后 1568×995，列缝仍剩约 2 个暗像素（灰度 148/2/0/56）；
深色画面未验，见 M2 风险。

`SHEET_MAX_WIDTH = 2560` 在这里作为**软预算**：加缝后 3×3 是 2562，超出 2px/格。
如果以后要求硬守 2560，必须把 `base` 的预算减 2（3×3 画面会从 852 变 850），不在本计划内；
token 估算一律按实际 `sheetWidth` 算，不写死 2556。

### 1.3 两条口径（要写进文档，免得以后又算错）

1. **「九宫格省 9 倍」不成立**。省 2 倍（不缩图）到 5 倍（缩到 1568），倍数由看图模型决定，
   插件控制不了；插件能控制的是「格子落在哪」和「告诉模型每格剩多少像素」。
2. **二手口径「一张图 384 token」不是这个实现**。384 token ≈ 730×410 整图、每格 243×137，
   那是主动放弃看清的档位；本实现整图约 5.3–5.4k token。按像素比约 **13.8–13.9 倍**（不是初稿写的 12 倍），
   按 token 比也约 13.9 倍，两边都接近 14 倍，成本数字不可直接比价。

token 数都是按 28px patch 的估算，只用来表达量级，不当验收指标。

## 3. 证据

### 3.1 论文（只取与本仓库有关的结论）

- **F-16（arXiv 2503.13956）**：把帧率提到 16 FPS 并在每秒内压 token，7B 在 Video-MME / TemporalBench SOTA，
  高速运动超过 GPT-4o、Gemini-1.5-Pro。它反对的基线是 **≤2 FPS**；本实现整条等间隔是 0.011 FPS。
  → 结论：九宫格只能回答「这条片子讲什么」，回答不了「动作怎么发生」。这是定位器的定位。
- **Stacked Temporal Attention（arXiv 2510.26027）**：把时序注意力放进视觉编码器，送 LLM 前就有帧间关系，
  VITATECS / MVBench / Video-MME 最高 +5.5%。→ 结论：拼图把时间轴压平成 2D，编码器拿不到时间结构；
  「格号 + 时间码」是模型唯一的时间通道，不是装饰。任何减少时间标签的改动都是在拆这条通道。
- **Why Is Video Still So Expensive?（arXiv 2609.10355）**：按抽帧 / 编码 / connector 减 token / prefill+decode
  四阶段组织省法。→ 结论：拼图只作用于第 1 阶段和输入 token 数；模型缩图后省下的又会以精度形式还回去。
  所以插件侧的正确动作是「把格子放对」+「说清每格剩多少」，不是继续压像素。
- **ReMoRa（arXiv 2602.16412）**：稀疏 RGB 关键帧 + 运动表示（当光流用），不解码完整 RGB 流。
  → 见 §5，不在本计划。

## 4. 里程碑

### M1 — 结果口径（与 M2 同批落地）

**改什么**

1. `ShotsResult` 增加四个可选字段：`sheetWidth` / `sheetHeight`（整图，含 M2 的 2px 格缝）与
   `cropWidth` / `cropHeight`（有 `--crop` 时裁切区域的原生像素，按播放流分辨率估）。
   - 整图公式固定为 `cols * (cellWidth + 2)` / `rows * (cellHeight + 2)`；M1 与 M2 同批，不保留「未加缝」分支，也不写死 2556。
   - 在拼图结束时填入；`readShotsCache` 对同版本缺字段的结果回填，`render` 对缺失字段 fallback。
   - `SHOTS_CACHE_VERSION` 7 → 8（见 M2）；旧 v7 缓存直接失效，回填不承担兼容 v7 的职责。
2. `feature.ts` 的 `render` 在现有「一格 …」那行后面补一句有效像素：
   - 先算 `scale = Math.min(1, 1568 / Math.max(sheetWidth, sheetHeight))`。整图已经小于 1568 时不放大。
   - 画面宽 `Math.round(cellWidth * scale)`；画面高 `Math.round((cellHeight - (labelHeight ?? 0)) * scale)`。
   - 多格（`capacity > 1`）：
     `按长边 1568 估算，每格画面约 521×293（含格号条 / 缝约 523×332）—— 字幕、专名、数字别在格子里认，用 at 指定那一秒 + grid 1x1 取单帧`
     —— 数字按上面的公式现算，不写死；没有格号条时是「含格间缝约」。
   - `grid 1x1`：
     - 无 `crop`：`这一格取的是画面源尺寸（最多 2560 长边），不再被九宫格二次缩小；能否认字仍取决于源清晰度 / 码率。`
     - 有 `crop`：`这一格的画面输出 W×H（裁切区域按 2560 长边以内的框缩放，裁切区域原生约 w×h）；输出尺寸不等于原生细节，能否认字仍取决于裁切区域的原生清晰度 / 码率。`
     不写「一定能认字」；也不把放大后的输出尺寸说成「裁切后的尺寸」。
3. `bili_shots` 的 description 补一句：
   `要核专名 / 数字 / 小字，用 grid 1x1 + at 指定那一秒取单帧；格子只用来定位。`
4. `commands.ts` 的 shots 收尾行也补同一句有效像素说明，CLI 与工具不要两套口径。
5. `SHOTS_CACHE_VERSION` 7 → 8（与 M2 同批：产物像素变了）；旧 v7 缓存直接失效，
   `readShotsCache` 的回填只作为同版本缺字段的防御。

**为什么**：S2。论文 3 条都指向同一件事——省下的像素会以错误的形式回来；把代价写在返回值里，
模型才会自己选「看清」还是「看全」。

**验收**

- 3×3 与 1×1 各跑一次：`render` 文案随 `capacity` 变，整图尺寸与 `sheetWidth` / `sheetHeight` 实测一致，
  画面尺寸按 `cellWidth` / `cellHeight - labelHeight` 复核；有字体时显示「含格号条 / 缝约 …」，不会把 `cellHeight` 当画面高。
- 1×1 + `--crop`：输出尺寸与 `cropWidth` / `cropHeight` 同时出现；文案不把输出尺寸当原生细节。
- `bun run check` 通过；v7 旧缓存失效一次，同版本缺字段时回填 / fallback 生效。
- 不新增网络调用。
- CLI 与工具文案一致。

**风险**：文案过长挤占上下文 —— 控制在一行内，不做多档表格；1568 是常见看图工具的长边，不是所有模型，
文案用「按长边 1568 估算」而不是承诺。1×1 + `--crop` 的输出可能远大于原生区域；
文案必须同时给原生像素，否则 M1 反而会放大自信。

### M2 — 格间分隔

**改什么**

1. 取帧时的 `scalePad` 末尾加 `pad=iw+2:ih+2:0:0:color=black`（黑边即底色，不引入新颜色），
   使每格实际为 `cw+2 × chp+2`，tile 后列与列之间有 2px 缝。
2. 黑图（缺帧占位）尺寸同步改成 `cw+2 × chp+2`，否则 tile 要求等大会失败。
3. `cellWidth` / `cellHeight` 的对外含义**保持现状**：`cellWidth` 是画面宽，`cellHeight` 是画面 + 格号条；
   不改成「画面高」（M1 的有效像素依赖这个区分）。
4. `sheetWidth` / `sheetHeight` 公式同步为 `cols × (cellWidth + 2)` / `rows × (cellHeight + 2)`。
   3×3 由此得到 2562×1626；`SHEET_MAX_WIDTH` 作为软预算记录，超出 2px/格，token 估算按 2562。
5. `SHOTS_CACHE_VERSION` 7 → 8（产物像素变了，旧缓存必须失效）。

**为什么**：S3。标签条只隔开了行，没隔开列；相邻两格共边时，模型容易把左格的物体算到右格
（笔记里的「绷带给了 GPT」就是这类错）。

**验收**

- 3×3 整图宽 = `3 × (852 + 2) = 2562`；有字体时高 = `3 × (540 + 2) = 1626`；肉眼能看到列缝。
- 把同一张图缩到长边 1568 再看一次，缝仍可辨（实测合成样片约 2 个暗像素）；若不可辨，按 §风险 调整。
- 深色画面（黑底幻灯片 / 夜间场景）再看一次列缝；纯黑缝在近黑背景上可能不可辨。
- 缺帧时黑格仍等大，拼图不报错。
- 旧缓存 key 失效一次，重跑结果正确；`sheetWidth` / `sheetHeight` 与实际图一致。

**风险**：2px 在缩到长边 1568 后只剩约 1.2px，JPEG 和缩放可能把它吃掉；只在必要时加，不无条件加粗。
若实测发现缩放后缝消失，先试 3px；仍不可辨再按 `cw` 比例升到 4–6px，但每档都要重跑同一组样本，确认模型不会把缝读成表格。
纯黑缝在近黑背景上可能和画面融在一起 —— 这类深色场景正是最容易串格的地方；若深色样片不可辨，
优先试 1px 中性灰（会引入新颜色，单独记一次实验），不要只把黑缝加宽。
若模型把缝读成「分栏」，先回退到 1px。
**任何缝宽 / 颜色调整都要再把 `SHOTS_CACHE_VERSION` +1**，否则旧图会被继续命中。

### M3 — 章节取帧

**改什么**

1. 新参数 `chapters`（bool，默认 false；CLI `--chapters`），`ShotsMode` 增加 `'chapters'`。
   - 与 `at` / `range` / `fps` / `diff` / `diffReport` / `diff-*` 互斥；同给时 usage 错误，提示「`--at` / `--range` / `--chapters` 三选一，diff 系列只配 `--range`」。
   - `chapters` 与 `--fps` 同给也必须报错，不能静默忽略。
   - `crop` / `grid` / `page` / `outDir` 仍可用。
   - CLI 的 usage / flag、`bili_shots` 的 `params` / `schema` / `execute` / `render` 都要加；
     `feature.ts:394` 的 `mode` 枚举加 `chapters`。
2. 实现：在拿到 `page` 之后调用 `getPlayerInfo(bvid, page.cid, credential)`，拿 `view_points`
   → `[{fromSec, title}]`。`page.cid` 来自 `getView` 的分 P，不是播放地址返回的；不新增 `lib/bilibili` 接口。
   `labelVf` 增加可选 `chapterNo`，烧成 `C3 1 12:30`（章节号 + 格号 + 时间码）。
3. 选点算法（抽成纯函数 `planChapterTimes`，便于单测；签名 `({chapters, capacity, span}) -> {times, labels, chapterNos, note?}`）：
   1. 归一化：`t = Number(from)`，丢弃非有限 / 小于 0 / 大于等于 `span` 的章节；`title` 去空白，空标题记 `第 N 章`（N 为排序后的序号）。
   2. 排序、去重：按 `t` 升序；同一时刻（差 < 0.5s）只留先到的一章；去重后再算章节时长。`maxT = max(0, span - 0.2)`。
   3. 章节区间：`[start, nextStart)`，最后一章到 `maxT`；时长 < 0.5s 的章节丢弃。
   4. 章节内三个候选点（都 clamp 到 `[0, maxT]`）：
      - 主帧（内容 / 结算常在后段）：`min(maxT, start + duration * 0.6)`；
      - 后段帧：`min(maxT, start + duration * 0.85)`，与主帧差 < 0.5s 时丢掉；
      - 起点帧：`min(maxT, start + min(0.5, duration * 0.1))`，只作补充，不优先。
      主帧是默认输出；起点帧不再作为「每章必出」的那一帧。
   5. 章节数 > 容量：先保第一条和最后一条（片头 / 结论不丢），中间按时长降序补到 `capacity`；
      每条只出主帧，再按时间排序；`note` 报「丢掉 N 章（越界 / 过短 / 超容量）」。
      章节数 ≤ 容量：每章先出主帧；再按时长降序补后段帧，最后补起点帧，直到满。
   6. 仍不足容量：用 `((i + 0.5) * maxT) / (capacity * 4)` 的等间隔候选池补齐（池取 `capacity * 4` 个候选），
      与已有点差 < 0.5s 的跳过；池用尽仍不足就少几格，并在 `note` 报实际数量。
   7. `capacity = 1`：取最长章节的主帧（不是起点帧）；没有章节时走原 `grid` 等间隔。
   8. 最后排序、clamp 到 `[0, maxT]`、保证严格递增；任何重复都丢弃。
   9. 每个时间点同时给出 `chapterNo`（1-based，补齐 / 片头点没有章节号）与 `label`（章节标题 / 「等间隔」/「序章前」）。
4. 数据契约：
   - `ShotsProgress` 的 `plan` 增加 `chapters?: Array<{fromSec, title}>`、`chapterLabels?: string[]`、`chapterNos?: number[]`（后两者与 `times` 等长）；
   - `ShotsResult` 增加同样三个字段（与 `timesSec` 等长）；
   - `chapterLabels[i]` 是该时间点的显示名：章节主帧 / 后段 / 起点都写章节标题，补齐点写「等间隔」，片头之前写「序章前」；
   - `chapterNos[i]` 是 1-based 章节序号；补齐 / 片头点没有序号；
   - 格号条烧成 `C3 1 12:30`（章节号 + 格号 + 时间码），标题不烧进图，避免长度不可控；
   - `chapterLabels` / `chapterNos` 与展平的 `timesSec` 对齐；render 按 `sheets[].timesSec.length` 切分到每张图；
   - `feature.ts` 的 schema / render 类型同步；render 优先用 `chapterLabels` / `chapterNos`，没有时再按「上一个 `fromSec` 的章节」回退；
   - CLI 进度在 `mode === 'chapters'` 时输出「章节 N 个 · M 个时间点」，逐格显示 `C3 标题`（标题截断到 20 字）；
     收尾的逐格时间码也带 `C3 标题`，没有就省略（退化结果不显示空标签）。
5. 失败退化：`getPlayerInfo` 抛错 / `view_points` 为空 → 退回今天的等间隔，不报错（与 `video()` 里章节失败只进 notes 的口径一致）。
   - 结果 `mode` 仍记 `chapters`（cacheKey 与普通 `grid` 分开），`chapters` / `chapterLabels` / `chapterNos` 为空；时间点和图片与今天的 `grid` 一致。
   - 抛错：`note` 写 `章节没读到，按等间隔抽的：<错误摘要>`，并**跳过 `writeShotsCache`**，避免一次 412 把退化结果缓存 7 天；
   - 空列表 / 全部章节被过滤：`note` 写 `这条没有可用章节（空 / 越界 / 过短），按等间隔抽的`；这是合法结果，可以正常缓存。
6. 缓存：
   - cacheKey 已有 `mode`，`chapters` 不需要再加一个标记；`mode=chapters` 已区隔。
   - 章节列表本身不在 key 里：UP 改章节后 7 天内可能看到旧帧，接受这个陈旧度；
     若以后不能接受，需要把 `getPlayerInfo` 提到 cache 查询之前并加章节指纹，另算一次 API 的成本。
   - `SHOTS_CACHE_VERSION` 已在 M2 升到 8，不重复升。
7. 测试前置：
   - 新增 `test/shots-chapters.test.ts`（或同层 `test/`），`package.json` 加 `"test": "bun test"`，
     并把 `check` 改成 `... && bun test`（或 CI 同跑），别留一个没人跑的 `test` 脚本；
     `tsconfig.json` 的 `include` 加 `test`，`tsconfig.build.json` 仍只构建 `src`；
     `devDependencies` 加 `@types/bun`（或 `bun-types`），`tsconfig.json` 的 `compilerOptions.types` 加 `bun`
     （现有只有 `node`），否则 `import { test } from 'bun:test'` 过不了 `tsc`。
   - 覆盖：0 章 / 1 章 / `capacity=1` / 章节数超容量 / 重复起点 / 重叠章节 / `from >= span` /
     0 秒起点 / 极短 span / `chapterLabels` / `chapterNos` 与 `times` 等长 / 严格递增 /
     超容量时首尾必在 / 主帧落在章节 60% 附近。
   - `bun test` 通过后才算 M3 完成。

**为什么**：S1 + S4。B 站章节就是 UP 手标的场景边界，比等间隔更接近「画面真的变了」；
而且它是一次已有接口的复用，不需要扫全片。这是本仓库能拿到的最便宜的「按场景数付费」。

**验收**

- 有章节的片子：`chapters` / `chapterLabels` / `chapterNos` 字段、终端进度与渲染都能把每个时间点对到章节；`timesSec` 严格递增。
- 章节数 > 容量：首尾章节必在，中间按最长补；`note` 报丢掉的数量；主帧落在章节 60% 附近，起点帧只在有余额时才出现。
- 无章节 / 接口失败：时间点和图片与今天的等间隔一致；`mode` / 进度文案 / `note` 会显示这是章节模式的退化结果。接口失败的结果不写缓存，重跑会重新尝试。
- `--chapters` 与 `--at` / `--range` / `--fps` / `--diff` / `--diff-report` / `--diff-*` 同给：usage 错误，提示互斥。
- 单测覆盖上面列出的边界，`bun test` 通过（并已接进 `check`）。

**风险**

- 章节是 UP 手标的：可能空、可能重叠、可能一条覆盖全片 → 已用过滤 + 去重 + 时长门槛 + 等间隔补齐处理。
- 主帧取 60% 是折中：太靠前是标题 / 转场，太靠后是黑场 / 下章预告；后段帧 85% 只作补充，起点帧 0.5s 只在有余额时才出。
  这个系数要拿真实章节片复核，验收按「主帧在章节内」检查，不要求逐字节等于某个比例。
- 多一次 API：失败必须静默退化且不缓存，不能让「本来能抽的帧」因为章节接口 412 而抽不出来。
- 章节标题只在 `note` / 进度 / render 里出现，不烧进图；格号条只烧 `C3` 这样的短序号 + 格号 + 时间码，
  标题长度不可控，放不进固定高度的格号条。

## 5. 不做的，以及为什么

| 项 | 为什么不做 |
|---|---|
| **ReMoRa 式压缩域**（I 帧 + 运动向量） | B 站直链是按 `-ss` 远程 seek，省的是带宽不是解码；要拿运动向量得先完整解码一遍，本地成本反而更高。它的场景是本地长视频推理，不是流式抽帧。 |
| **F-16 式 16 FPS** | 40 帧上限 + 逐帧远程 seek，10 分钟片子要 9600 帧，一次几十秒的网络往返。那是模型侧（每秒内压 token）的解法，插件侧只能把 9–16 格放对位置。 |
| **整条视频自动切点扫描** | 要先密抽全片再算 SSIM，成本正好是 `--range --diff` 的反面；对「先看一眼」的默认路径不划算。留着 `--range` 让 agent 在自己关心的段落用。 |
| **把帧落盘做长期缓存** | 已有 7 天 / 40 张的 `SHOTS_DIR` 缓存；跨进程共享是另一个账（谁付费、怎么失效），单独排。 |
| **按分区自动降格 / 自动 4×4** | 规则可解释性差，容易在「知识区但画面是动画」上判错；等 M1 的有效像素提示上线后，让模型自己选更稳。 |

## 6. 待议（不阻塞本计划）

- **按 `tname` 分区默认 2×2**：`科技` / `知识` / `编程` 区默认 `grid 2x2`，其余 3×3。需要先有 M1 的
  有效像素提示跑一段时间，看模型是否已经会自己选。
- **超长视频提示 4×4 / 多张**：>10 分钟时 `note` 里建议 `--grid 4x4` 或 `--chapters`，只提示不强制。
- **`--diff` 开放到整条**：需要先量一次「密抽 1fps 全片」在真实网络下的耗时，再决定值不值。
- **硬守 `SHEET_MAX_WIDTH`**：若 2px 软预算不可接受，把 `base` 预算减 2（3×3 画面 850×478、tile 852×542、整图 2556×1626），
  是另一个小改，不和本计划的章节逻辑绑定。
- **1×1 + `--crop` 不放大**：把 `base` 夹到裁切区域原生长边，输出直接用原生尺寸（不给假清晰）；
  会改变 crop 的格子尺寸，先看当前的「输出 / 原生」双数字文案是否够用。
